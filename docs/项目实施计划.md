# ClassNest 项目实施计划

> 依据：`docs/tech.md` 第 59-63 节（Vibe Coding 阶段、Completion Rule、DoD、MVP DoD、最终产品结构）。

---

## 1. 实施原则

1. 开发顺序严格按 Phase 0 → Phase 10，禁止跨阶段大量开发；
2. 每个 Phase 开始前：先读现有代码 → 检查目录 → 检查 migration → 检查模型 → 不重复创建已有模块；
3. 每个 Phase 内部顺序：领域逻辑 → Repository → Store → UI → 自动补充测试；
4. 修改优先 small patch，不做无理由的架构重写；重大架构修改必须说明原因；
5. 未通过当前 Phase 验收标准，不得自行进入下一阶段；
6. 任何一个功能必须同时满足 DoD（代码 + UI + 持久化 + 错误处理 + 测试 + 重启验证）才算完成。

## 3. Phase 0：项目骨架

**目标**：建立 Vue 3 + Vite + TS + Naive UI + Pinia + Router + Tauri 2 + SQLite 可运行骨架。

**工作内容**

- 初始化 Vite + Vue 3 + TypeScript 工程，接入 SCSS；
- 建立 `src/views|components|stores|models|engine|repositories|database|importers|exporters|services|utils|router` 目录骨架；
- 建立 `src-tauri/`（main.rs / lib.rs / commands / capabilities / tauri.conf.json），引入 `@tauri-apps/plugin-sql`；
- SQLite 连接与迁移执行（0001-0004 按 docs/数据库设计.sql 拆分实现）；
- App.vue：Naive UI Provider（NMessageProvider / NDialogProvider / NNotificationProvider）+ RouterView + 基础布局；
- 路由表初建（页面可空壳运行）。

**验收标准**

```text
[ ] npm run build 成功
[ ] Tauri dev 成功
[ ] SQLite 成功创建
[ ] migration 执行成功
[ ] 重启应用数据库仍存在
[ ] Naive UI provider 正常
```

**测试**：迁移可重复执行（幂等）、数据库连接初始化测试。

## 4. Phase 1：Schedule Core

**目标**：完成 Schedule / Course / CourseSession 三类核心数据与基础交互。

**工作内容**

- models：schedule.ts / course.ts / session.ts / timetable.ts；
- repositories：ScheduleRepository / CourseRepository / CourseSessionRepository；
- stores：scheduleStore / courseStore 核心动作；
- 新建课表：同流程创建 schedule + 默认 timetable + 默认 schedule_style；
- 课程 CRUD：新增 / 编辑 / 删除（NDialog 确认），一个课程支持多个时间段；
- 时间段编辑：星期、起止节次、周数（结构化 WeekRule，禁止直接操作字符串）、老师、地点、自定义时间；
- 主课表基础展示：ScheduleHeader / WeekNavigator / ScheduleGrid 骨架 / CourseCard；
- 空状态：无课表时显示「创建课表 / 导入课表」，禁止白屏。

**验收标准**

```text
[ ] 可以创建课表
[ ] 可以创建课程
[ ] 可以删除课程
[ ] 一个课程可以有多个时间段
[ ] 重启后数据存在
[ ] 切换周正确
[ ] 当前星期有视觉标记
```

## 5. Phase 2：Schedule Engine

**目标**：把周数、日期、冲突、位置计算全部收敛到 `src/engine/`，UI 只消费 `RenderedCourse[]`。

**工作内容**

- weekRuleEngine：`isWeekMatched()` / `getMatchedWeeks()`；
- dateEngine：`getDateOfWeek()` / `getCurrentWeek()`，正确处理跨月、跨年、周一/周日起始；
- conflictEngine：`detectConflicts()`，weekday 相同 + week 相交 + section 相交；自定义时间附加时间判断；冲突保留两个课程；
- positionEngine：`getCoursePosition()` 计算 top / height / left / width，主课表不负责计算；
- scheduleEngine：整合输出 `RenderedCourse`（含 weekMatched / conflict / opacity / top / height）；
- 主课表改造为 CSS Grid + absolute positioning（禁止 NDataTable / table）。

**验收标准（必须全部通过）**

```text
[ ] 1-16 周
[ ] 1-8 单周
[ ] 2-16 双周
[ ] 1-5、7-11
[ ] 多时间段
[ ] 课程冲突
[ ] 跨月
[ ] 跨年
[ ] 自定义时间
```

**测试**：这是重点阶段，上述用例必须有 engine unit tests；本阶段完成前禁止继续大量开发 UI。

## 6. Phase 3：多课表

**目标**：多课表切换、管理与数据隔离。

**工作内容**

- ScheduleSwitcher（NDropdown 切换课表名）；
- ScheduleManager（/schedules：查看、切换、新增、复制、重命名、删除）；
- ScheduleCreateDialog（NModal/Drawer：名称、学期开始、总周数、当前周、每天节数）；
- 删除课表：NDialog 明确提示级联删除课程、时间段、调课与外观。

**验收标准**

```text
[ ] 创建多个课表
[ ] 每个课表数据隔离
[ ] 每个课表有自己的外观
[ ] 每个课表有自己的时间表
[ ] 删除课表不会影响其他课表
```

## 7. Phase 4：外观

**目标**：ScheduleStyle 完整可配置，实时预览。

**工作内容**

- ScheduleAppearanceForm：背景、课程颜色、圆角、透明度、课程高度、网格、显示时间/地点/老师、显示非本周课程；

- 保存策略统一：普通字段保存按钮，外观设置实时保存。

**验收标准**

```text
[ ] 设置即时预览
[ ] 重启后保留
[ ] 切换课表互不影响
[ ] 深色/浅色 UI 正常
```

## 8. Phase 5：CSV 导入 / 导出

**目标**：第一批导入导出能力交付。

**工作内容**

- types.ts / registry.ts：统一 `CourseImporter` 接口与注册表；
- CsvImporter：课程名称、星期、开始节、结束节、老师、地点、周数；
- 导入管线：Parse → Validate → Preview → Confirm → Database，禁止解析后直接写库；
- ImportPreview：课程数 / 时间段数 / 异常数 / 冲突数，状态 ✓ / ⚠ / ✕；ImportErrorList；NAlert；
- csvExporter：CSV 导出，默认当前课表、支持全部课表；
- ImportView / ExportView 页面接入。

**验收标准**

```text
[ ] CSV 可以导入
[ ] 导入前有预览
[ ] 错误不会直接写入 DB
[ ] 用户确认后才提交
[ ] CSV 可以导出
[ ] 导出后重新导入数据一致
```

**测试**：importer tests（正常、异常行、跨周规则、冲突统计）。

## 9. Phase 6：Backup / Restore / ICS

**目标**：完整 JSON 备份、事务恢复、ICS 导出。

**工作内容**

- backupService：当前课表或全部课表的完整 JSON（version / exportedAt / schedules / courses / courseSessions / overrides / timetables / scheduleStyles）；
- BackupImporter：验证版本 → 验证结构 → 检查引用关系 → 预览 → 确认 → 事务写入，失败回滚；
- icsExporter：DTSTART / DTEND / SUMMARY / LOCATION / DESCRIPTION，明确不生成 VALARM；
- services/fileService（Tauri command 读写文件）。

**验收标准**

```text
[ ] 完整备份
[ ] 完整恢复
[ ] 恢复失败自动回滚
[ ] 版本字段存在
[ ] ICS 正常
[ ] ICS 不生成 VALARM
```

## 10. Phase 7：调课

**目标**：CourseOverride 支持 move / cancel / replace。

**工作内容**

- models / migration 追加（0005_course_override 如已内置则复用现有表）；
- OverrideEditor：原始日期、类型、目标日期、节次、地点、老师、备注；
- ScheduleEngine 接入：原课程 + Override = 最终课程，只影响指定日期。

**验收标准（必须通过）**

```text
周一数学 → 调到周三
只影响指定日期
下一周数学仍保持原安排
```

**测试**：移动、取消、替换、日期边界、级联删除。

## 12. Phase 9：自动备份

**目标**：每天首次启动检查并自动备份。

**工作内容**

- BackupScheduler：每天首次启动 → 检查上次备份时间 → 自动创建备份；
- BackupManager：默认关闭；开启后保留最近 10 个备份，自动删除旧备份；
- 手动备份、恢复入口并入 /export、/import。

**验收标准**

```text
[ ] 开启后自动生成
[ ] 最多保留 10 个
[ ] 删除旧备份
[ ] 用户可手动备份
[ ] 用户可以恢复
```

## 17. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 周数/日期逻辑出错 | Phase 2 强制单测完毕后才继续 UI；禁止在组件/CSS 中实现 |
| 冲突课程实现过重 | 冲突仅保留两个课程 + 位置引擎拆分左右，不做删除 |
| 导入直接写库造成脏数据 | 强制 Parse → Validate → Preview → Confirm 管线 |
| 恢复失败破坏数据 | 事务写入 + 失败回滚，恢复前校验版本与引用关系 |
| 跨阶段蔓延 | 严格执行 Completion Rule，未过验收不进入下一阶段 |
| 性能退化 | 课程只加载一次并进 Pinia 缓存，切周不查库 |

## 18. 最终产品形态

用户打开应用直接看到主课表，理解不了也不需要理解任何数据库概念：

```text
┌──────────────────────────────────────────┐
│ 我的大学课表   第 6 周      ＋  导入 ⋯ │
├────────┬─────────────────────────────────┤
│        │ 周一 周二 周三 周四 周五 周六 日 │
├────────┼─────────────────────────────────┤
│ 08:00  │ 数学      英语                  │
│        │ 数学      英语                  │
├────────┼─────────────────────────────────┤
│ 10:00  │      数据库                     │
│        │      数据库                     │
├────────┼─────────────────────────────────┤
│ 14:00  │ 软件工程                        │
│        │ 软件工程                        │
└────────┴─────────────────────────────────┘
```

所有复杂数据模型（WeekRule / CourseSession / CourseOverride / ScheduleStyle / TimeTable / Conflict）全部隐藏在系统内部。用户只需要：看到课、点击课、编辑课、切周、切课表、导入、导出。
